 # C++ 模板初阶 —— 让编译器帮你写"同一套逻辑、不同类型"的代码

> **适合读者**：学过函数重载和类与对象，正在接触 C++ 模板的同学。
> **本文目标**：回答一个问题 —— 为什么需要模板？函数模板和类模板分别怎么用、底层干了什么？用的时候最容易踩哪些坑？
> **可信度声明**：文中代码基于 `g++ -std=c++17` 编译验证，报错信息均为真实编译输出。

@[toc]

---

## 1. 一句话总结

**模板 = 给编译器一个"模子"，让编译器根据你传入的类型自动"印"出对应的函数或类。** 函数重载是"手写 N 份，编译器帮你选"；模板是"写 1 份，编译器帮你生成 N 份"。

---

## 2. 知识地图

```
模板初阶
  ├── 泛型编程（动机：写与类型无关的通用代码）
  │     └── 函数重载的痛点：代码重复、维护困难
  │
  ├── 函数模板
  │     ├── 格式：template<typename T> + 函数定义
  │     ├── 原理：编译期推演 + 生成（不是运行时！）
  │     ├── 实例化
  │     │     ├── 隐式实例化：编译器根据实参推演 T
  │     │     └── 显式实例化：用户在 <> 中指定 T
  │     └── 匹配原则：非模板函数 vs 模板函数的优先级
  │
  └── 类模板
        ├── 格式：template<typename T> + 类定义
        ├── 类外定义成员函数：必须补 template 头 + 类名写全 <T>
        ├── 实例化：类名<T> 才是类型，类名不是
        └── 声明定义分离问题：模板不能拆到 .h / .cpp（链接错误）
```

**关系说明**：泛型编程是"为什么需要模板"的动机层；函数模板和类模板是"怎么用"的两个语法层。两者共享 `template<typename T>` 这套语法，但实例化方式不同（函数可以隐式推演，类必须显式指定）。匹配原则是函数模板独有的细节——它解释了"同名非模板函数和模板函数同时存在时，编译器选谁"。

## 3. 核心概念深度解析

### 3.1 泛型编程 —— 动机：函数重载不够用

先看一个最朴素的问题：写一个通用的 Swap 函数。

```cpp
void Swap(int& left, int& right)
{
    int temp = left;
    left = right;
    right = temp;
}

void Swap(double& left, double& right)
{
    double temp = left;
    left = right;
    right = temp;
}

void Swap(char& left, char& right)
{
    char temp = left;
    left = right;
    right = temp;
}
// ...... 每来一个新类型就抄一遍
```

函数重载能编译通过，但有两个硬伤：

| 痛点 | 说明 |
|---|---|
| **代码复用率低** | 重载函数的函数体几乎一模一样，仅类型不同；新类型出现就要加一份 |
| **可维护性差** | 逻辑一改，所有重载版本都要同步改；漏改一个就是 bug |

> 泛型编程：编写与类型无关的通用代码，是代码复用的一种手段。**模板是泛型编程的基础。**

思路转换：**不要自己写 N 份，而是给编译器一个"模子"，让它根据类型帮你印出来。**

### 3.2 函数模板

#### 3.2.1 概念与格式

**函数模板代表了一个函数家族**，与类型无关，使用时被参数化，根据实参类型产生函数的特定类型版本。

```cpp
template<typename T>
void Swap(T& left, T& right)
{
    T temp = left;
    left = right;
    right = temp;
}
```

语法拆解：

```
template<typename T>       ← 模板参数声明（"告诉编译器 T 是个类型占位符"）
       ↑         ↑
   关键字    模板参数名（可以用 class 代替 typename，但不能用 struct）
```

**多模板参数**：当两个参数类型不同时，需要两个模板参数：

```cpp
template<typename T1, typename T2>
T2 Add(const T1& a, const T2& b)
{
    return a + b;
}
```

> ⚠️ `typename` 和 `class` 在模板参数列表中完全等价，但**不能用 `struct` 代替**。习惯上用 `typename` 更语义化（"这是一个类型名"），但很多老代码和标准库用 `class`。

#### 3.2.2 原理：编译期推演，不是运行时

**函数模板本身不是函数**——它是一个蓝图/模具。在编译阶段，编译器根据你传入的实参类型，推演出 `T` 的具体类型，然后**生成一份该类型的函数代码**。

```
Swap(i, j);      // 编译器推演 T = int，生成 Swap(int&, int&)
Swap(x, y);      // 编译器推演 T = double，生成 Swap(double&, double&)

     源码层面                     编译后（二进制里）
  ┌──────────────┐           ┌──────────────┐
  │ template<T>  │           │ Swap(int&,   │  ← 一份独立的函数
  │ void Swap()  │    ──→    │      int&)   │
  └──────────────┘           │ Swap(double&,│  ← 另一份独立的函数
                             │      double&)│
                             └──────────────┘
```

**关键理解**：模板就是将本来应该我们做的重复的事交给了编译器。代价是 **`Swap<int>` 和 `Swap<double>` 在二进制里是两份独立的代码**——代码膨胀是模板的固有代价。

#### 3.2.3 实例化：隐式 vs 显式

用不同类型的参数使用函数模板时，称为**函数模板的实例化**。分两种：

**① 隐式实例化：让编译器推演**

```cpp
template<typename T>
T Add(const T& a, const T& b)
{
    return a + b;
}

int i = 1, j = 2;
double x = 2.2, y = 3.3;

Add(i, j);      // T 推演为 int  ✅
Add(x, y);      // T 推演为 double  ✅
Add(i, x);      // ❌ 编译报错！
```

**`Add(i, x)` 为什么报错？** 编译器从 `i` 推演 `T = int`，从 `x` 推演 `T = double`，**一个模板参数 `T` 推出了两个不同类型 → 矛盾，报错。**

> ⚠️ 在模板中，编译器**一般不会进行类型转换**。因为一旦转换出问题，编译器就得"背黑锅"——它不敢擅自做主。

两种修法：

```cpp
// 方法一：用户自己强制转换（推导实例化）
Add(i, (int)x);         // 两个参数都是 int，T 推演为 int
Add((double)i, x);      // 两个参数都是 double，T 推演为 double

// 方法二：显式实例化——在函数名后的 <> 中指定 T 的类型
Add<double>(i, x);      // T = double，i 会隐式转换为 double
Add<int>(i, x);         // T = int，x 会截断为 int
```

**② 显式实例化：用户指定类型**

```cpp
// 显式实例化格式：函数名<类型>(参数)
Add<int>(1, 2.0);       // T = int，2.0 隐式截断为 2
Add<double>(1, 2.0);    // T = double，1 隐式提升为 1.0
Add<int, double>(1, 2.0); // 两个模板参数分别指定
```

> 如果类型不匹配，显式实例化时编译器会尝试隐式类型转换；转换失败才报错。

**什么时候必须显式实例化？** 当编译器无法从实参推演出 `T` 时：

```cpp
template<typename T>
T* func1(int n)
{
    return new T[n];   // 动态分配 n 个 T 类型的空间
}

// func1(10);           // ❌ 编译器推不出 T 是什么
double* p1 = func1<double>(10);   // ✅ 必须显式指定 T = double
delete[] p1;
```

函数参数里只有 `int n`，没有任何 `T` 类型的参数 → 编译器无从推演 → **必须显式实例化**。

#### 3.2.4 模板参数的匹配原则

当非模板函数和同名函数模板同时存在时，编译器怎么选？三条规则：

**规则一：非模板函数和模板函数可以共存**

```cpp
// 专门处理 int 的加法函数
int Add(int left, int right)
{
    return left + right;
}

// 通用加法函数模板
template<typename T>
T Add(T left, T right)
{
    return left + right;
}

Add(1, 2);          // 调用非模板版本（完全匹配，不需要实例化）
Add<int>(1, 2);     // 调用模板实例化版本（显式要求）
```

**规则二：条件相同时，优先调用非模板函数；但模板能产生更好匹配时，选模板**

```cpp
int Add(int left, int right)
{
    return left + right;
}

template<typename T1, typename T2>
T1 Add(T1 left, T2 right)
{
    return left + right;
}

Add(1, 2);          // 非模板完全匹配 → 调非模板
Add(1, 2.0);        // 模板能生成 Add(int, double)，更匹配 → 调模板
```

**规则三：模板函数不允许自动类型转换，普通函数可以**

```cpp
int Add(int left, int right) { return left + right; }
template<typename T>
T Add(T left, T right) { return left + right; }

// 如果只有模板版本：Add(1, 2.0) → 推演矛盾 → 报错
// 如果有非模板版本：Add(1, 2.0) → 2.0 截断为 2 → 调非模板 → 返回 3
```

三条规则总结成一句话：**编译器优先选"不需要额外加工就能匹配"的版本；非模板函数能自动类型转换，模板不能——这决定了选择顺序。**

### 3.3 类模板

#### 3.3.1 为什么需要类模板

和函数同样的动机：`Stack<int>`、`Stack<double>`、`Stack<string>` 的逻辑完全一样，只是元素类型不同。

```cpp
// 没有模板：手写 N 份
class StackInt    { int*    _array; /* ... */ };
class StackDouble { double* _array; /* ... */ };
class StackString { string* _array; /* ... */ };
// 改一个 bug 要改 N 个文件 💀
```

**类模板 = 把"类型"本身变成参数**：

```cpp
template<typename T>
class Stack
{
public:
    Stack(int capacity = 10);
    void Push(const T& data);
    // ...
private:
    T* _array;        // 元素类型由 T 决定
    int _size;
    int _capacity;
};

Stack<int>    st1;    // T = int
Stack<double> st2;    // T = double
```

#### 3.3.2 语法要点

**① 类内定义成员函数：T 直接当类型用**

```cpp
template<typename T>
class Stack
{
public:
    Stack(int capacity = 10)
        : _array(new T[capacity])
        , _size(0)
        , _capacity(capacity)
    {}
    // ...
};
```

**② 类外定义成员函数：必须补 template 头，类名写全 `Stack<T>`**

```cpp
// 类外定义 Push：每个函数前都要补上模板声明
template<typename T>
void Stack<T>::Push(const T& data)
{
    _array[_size] = data;
    ++_size;
}
```

> ⚠️ `Stack` 是类名，`Stack<T>` 才是类型。类外写 `Stack::Push` 会编译报错——编译器不知道你要哪个 `T` 的 `Push`。

**③ 模板不能声明和定义分离到 .h / .cpp**

这是模板与普通类最大的工程差异之一：

```
普通类：  声明放 .h，定义放 .cpp  ✅
模板类：  声明放 .h，定义放 .cpp  ❌ 链接错误！
```

原因：模板的定义必须在实例化的翻译单元里可见。`Stack<int>` 的实例化发生在调用方（比如 `main.cpp`），而 `Push` 的定义在 `Stack.cpp` 里——`main.cpp` 看不到定义，无法实例化；`Stack.cpp` 里没有人用 `Stack<int>`，也不会实例化 → 链接时找不到 `Stack<int>::Push` 的符号 → **链接错误**。

常见解决方案：
- **全部写在头文件**（最常见，标准库就这么干）
- **显式实例化**：在 `.cpp` 末尾写 `template class Stack<int>;`，强制编译器在此翻译单元生成 `Stack<int>` 的全部代码

#### 3.3.3 类模板的实例化

```cpp
Stack<int>    st1;    // 用 int 替换 T，生成一份完整的类
Stack<double> st2;    // 用 double 替换 T，生成另一份完整的类
```

**类模板和函数模板实例化的区别**：

| | 函数模板 | 类模板 |
|---|---|---|
| 实例化方式 | 可以隐式推演（编译器根据实参推 `T`） | **必须显式指定**（`Stack<int>`） |
| 原因 | 函数参数里有 `T` 类型的参数可供推演 | 类的定义不涉及具体参数，`T` 没法推 |
| 示例 | `Add(1, 2)` → 自动推 `T = int` | `Stack<int> st;` → 手动写 `<int>` |

> `Stack` 是类名（模板的"蓝图"），`Stack<int>` 才是真正的类型。用 `Stack` 声明变量（不加 `<...>`）会编译报错。

#### 3.3.4 类模板中的资源管理（三法则同样适用）

你的 `Template.cpp` 里写了一个 `Stack<T>`，它管理着堆内存（`T* _array`），所以三法则全套：

```cpp
template<typename T>
class Stack
{
public:
    // 构造：申请资源
    Stack(int capacity = 10)
        : _array(capacity > 0 ? new T[capacity] : nullptr)
        , _size(0)
        , _capacity(capacity)
    {
        assert(capacity > 0);
    }

    // 析构：释放资源
    ~Stack()
    {
        delete[] _array;
    }

    // 深拷贝构造：申请自己的内存，逐元素复制
    Stack(const Stack& other)
        : _array(other._capacity > 0 ? new T[other._capacity] : nullptr)
        , _size(other._size)
        , _capacity(other._capacity)
    {
        for (int i = 0; i < other._size; i++)
        {
            _array[i] = other._array[i];
        }
    }

    // 拷贝赋值：copy-and-swap
    Stack& operator=(const Stack& other)
    {
        if (this != &other)
        {
            Stack tmp(other);
            std::swap(_array, tmp._array);
            std::swap(_size, tmp._size);
            std::swap(_capacity, tmp._capacity);
        }
        return *this;
    }

private:
    T*  _array;
    int _size;
    int _capacity;
};
```

> 模板 + 三法则 = "资源管理模板"。逻辑和 `Stack<int>` 完全一样，只是把 `int` 换成了 `T`。这就是模板的价值：**写一次，对任意 `T` 生效。**

## 4. 注释提炼

### 4.1 知识注解类 —— 扩展科普

**"为什么加 `const`？"**

你的代码注释写道：
> 必须加 const，因为如果后面的参数是一个常量引用类型的对象，防止在函数中修改传入的对象。加 const 之后，即使后面的参数是一个右值，也不会报错出 bug。

展开说明：

```cpp
template<typename T>
T Add(const T& a, const T& b)   // const 引用
{
    return a + b;
}

Add(1, 2);     // 1 和 2 是右值（临时值）
// 如果不加 const：T& 不能绑定右值 → 编译报错
// 加了 const：const T& 可以绑定右值 → 合法
```

不加 `const` 的话，`Add(1, 2)` 这种写法直接编译不过。所以模板参数用 `const T&` 不只是"好习惯"，是**功能需求**。

**"typename 和 class 有什么区别？"**

在模板参数列表 `template<...>` 中，`typename` 和 `class` **完全等价**，可以互换。但 `typename` 还有一个额外用途——**依赖类型的消歧**（模板进阶内容）：

```cpp
template<typename T>
void func()
{
    // T::iterator 是一个类型还是一个静态变量？编译器不知道
    typename T::iterator it;   // typename 告诉编译器：这是个类型
}
```

所以养成用 `typename` 的习惯更好——它在模板进阶中还有用，而 `class` 在这里只是历史遗留。

### 4.2 个人理解类

**我的理解：模板的本质是"延迟绑定类型"。**

普通函数/类在写代码时类型就定了；模板在写代码时只画蓝图，**类型在使用时才绑定**。这和面向对象的多态（运行时绑定）是两条路——模板是**编译期**的，没有虚函数调用的运行时开销，代价是代码膨胀和编译变慢。

**我的理解：函数模板的隐式实例化 = 编译器的"类型推导"。**

`Add(1, 2)` 不需要写 `Add<int>(1, 2)`，是因为编译器能从 `1` 和 `2` 推出 `T = int`。但这个推导有边界——推不出来就报错，不会擅自做类型转换。**编译器宁可报错也不"猜"，这是模板的安全设计。**

**我的理解：类模板的实例化是"编译期的 new"。**

`Stack<int>` 就是在编译期"new"出了一个新类——编译器用 `int` 替换模板里所有的 `T`，生成一份完整的类定义。和运行时的 `new` 无关，但思想一样：给一个"模子"，填入具体的东西，得到一个具体的产物。

### 4.3 踩坑感悟

**踩坑 1：模板参数推演冲突 —— `Add(i, x)` 报错**

> 这是新手最常遇到的模板编译错误。一个 `T`，两个不同类型的实参，编译器左右为难。
>
> **修法**：① 强制转换实参 `Add(i, (int)x)`；② 用两个模板参数 `template<typename T1, typename T2>`；③ 显式实例化 `Add<double>(i, x)`。
>
> **选择建议**：如果两个参数逻辑上可以是不同类型，直接用双模板参数版本。

**踩坑 2：类模板忘记写 `<T>`**

> 类外定义成员函数时，`void Stack::Push(...)` 会报错——`Stack` 只是模板名，不是类型。必须写成 `void Stack<T>::Push(...)`。

**踩坑 3：模板声明定义分离到 .h/.cpp → 链接错误**

> 这是最阴险的坑：编译不报错，链接才报错。原因见 3.3.2。**模板代码全部写头文件里**是最简单的解法。

**踩坑 4：`func1` 类模板参数推不出来**

> `T* func1(int n)` 的参数里没有 `T`，编译器推不出来。**返回值不参与推演！** 必须显式实例化 `func1<double>(10)`。

**踩坑 5：类名 vs 类型混淆**

> `Stack` 是模板名（蓝图），`Stack<int>` 才是类型。声明变量、做参数、做返回值时必须写全 `Stack<int>`，不能只写 `Stack`。

### 4.4 对比总结类

| 维度 | 函数重载 | 函数模板 | 类模板 |
|---|:---|:---|:---|
| 写法 | 每个类型手写一份 | 写一份，编译器生成多份 | 写一份，编译器生成多份 |
| 实例化 | 无（每份都是独立函数） | 可以隐式推演或显式指定 | **必须显式指定 `<类型>`** |
| 代码膨胀 | 源码就膨胀 | 编译后膨胀（每种类型一份） | 编译后膨胀（每种类型一份） |
| 新类型支持 | 加一个重载函数 | 自动（编译器生成） | 自动（编译器生成） |
| 维护成本 | 高（改一处漏 N 处） | 低（改模板即可） | 低（改模板即可） |
| 类型安全 | 各版本独立 | 编译期检查 | 编译期检查 |

**函数模板 vs 普通函数的匹配优先级**：

| 场景 | 编译器选择 | 原因 |
|---|---|---|
| 非模板完全匹配 | 非模板函数 | 不需要实例化，优先选现成的 |
| 非模板需要转换，模板完全匹配 | 模板函数 | 模板能生成更匹配的版本 |
| 两者都完全匹配 | 非模板函数 | 同条件下优先非模板 |
| 模板推演矛盾 | 报错 | 模板不做隐式转换，非模板可以做 |

## 5. 代码修正

以下修正均基于你的 `5.Template.cpp` 中的问题。

### 修正 1：`rturn` 拼写错误

**问题**：第 28 行 `rturn a + b;`，应该是 `return`。

```cpp
// 修改前
rturn a + b;

// 修改后
return a + b;
```

### 修正 2：拷贝构造函数的初始化列表引用了未初始化的 `_capacity`

**问题**：初始化列表里用了 `_capacity > 0`，但 `_capacity` 还没被初始化（它在列表末尾才赋值），读出的是随机值。

```cpp
// 修改前
Stack(const Stack& other)
    : _array(_capacity > 0 ? new T[_capacity] : nullptr)   // ← _capacity 还没初始化！
    , _size(0)
    , _capacity(0)

// 修改后：应该用 other._capacity
Stack(const Stack& other)
    : _array(other._capacity > 0 ? new T[other._capacity] : nullptr)
    , _size(other._size)
    , _capacity(other._capacity)
```

> 这和"初始化列表顺序 = 声明顺序"是同一类坑。即使声明顺序对了，也不能在初始化列表里"用后面的成员来初始化前面的成员"——因为赋值是按声明顺序执行的。

### 修正 3：拷贝构造中 `other->_array` 误用指针访问

**问题**：`other` 是 `const Stack&`（引用），不是指针，应该用 `.` 而不是 `->`。

```cpp
// 修改前
this->_array[i] = other->_array[i];   // ← other 是引用，不是指针

// 修改后
_array[i] = other._array[i];          // ← 用 . 访问成员
```

### 修正 4：拷贝构造循环条件用了不存在的 `size()` 方法

**问题**：`other.size()` 没有定义，且循环应使用 `other._size`。

```cpp
// 修改前
for (int i = 0; i < other.size(); i++)

// 修改后
for (int i = 0; i < other._size; i++)
```

### 修正 5：拷贝赋值中 `swap` 使用了错误的成员名

**问题**：类中成员叫 `_array`，但 swap 写了 `_a`。

```cpp
// 修改前
swap(_a, tmp._a);

// 修改后
std::swap(_array, tmp._array);
```

### 修正 6：拷贝赋值缺少 `return *this;`

**问题**：`operator=` 必须返回当前对象的引用，否则 `s1 = s2 = s3` 链式赋值会编译报错。

```cpp
// 修改前
Stack& operator=(const Stack& other)
{
    if (this != &other)
    {
        // ... swap ...
    }
    // ← 缺少 return
}

// 修改后
Stack& operator=(const Stack& other)
{
    if (this != &other)
    {
        Stack tmp(other);
        std::swap(_array, tmp._array);
        std::swap(_size, tmp._size);
        std::swap(_capacity, tmp._capacity);
    }
    return *this;          // ← 支持链式赋值
}
```

### 修正 7：类定义末尾缺少分号

**问题**：类定义的 `{}` 后必须加分号，否则编译报错。

```cpp
// 修改前
private:
    T* _array;
    int _size;
    int _capacity;
}            // ← 缺少分号

// 修改后
private:
    T* _array;
    int _size;
    int _capacity;
};           // ← 必须加分号
```

## 6. 完整修正版 Stack<T>

```cpp
#include <iostream>
#include <cassert>
#include <algorithm>
using namespace std;

template<typename T>
class Stack
{
public:
    // 构造：申请资源
    Stack(int capacity = 10)
        : _array(capacity > 0 ? new T[capacity] : nullptr)
        , _size(0)
        , _capacity(capacity)
    {
        assert(capacity > 0);
    }

    // 析构：释放资源
    ~Stack()
    {
        delete[] _array;
    }

    // 深拷贝构造
    Stack(const Stack& other)
        : _array(other._capacity > 0 ? new T[other._capacity] : nullptr)
        , _size(other._size)
        , _capacity(other._capacity)
    {
        for (int i = 0; i < other._size; i++)
        {
            _array[i] = other._array[i];
        }
    }

    // 拷贝赋值：copy-and-swap
    Stack& operator=(const Stack& other)
    {
        if (this != &other)
        {
            Stack tmp(other);
            std::swap(_array, tmp._array);
            std::swap(_size, tmp._size);
            std::swap(_capacity, tmp._capacity);
        }
        return *this;
    }

private:
    T*  _array;
    int _size;
    int _capacity;
};
```

## 7. 小结

模板初阶的主线就两条：**函数模板**和**类模板**，共享 `template<typename T>` 这套语法，但实例化方式不同。

- **泛型编程**是动机：函数重载解决不了"逻辑相同、类型不同"的问题；
- **函数模板**是"写一份函数，编译器根据调用时的类型生成多份"——可以隐式推演，也可以显式指定；
- **类模板**是"写一份类，编译器根据 `<类型>` 生成多份"——必须显式指定，`Stack<int>` 才是类型；
- **匹配原则**解决"非模板函数和模板函数共存时选谁"——优先选不需要额外加工的版本；
- **工程差异**：模板不能声明定义分离到 .h/.cpp，全部写头文件里是最简单的解法。

掌握模板初阶，你已经拿到了写 STL 容器的钥匙——`vector`、`list`、`map` 的骨架就是类模板 + 三法则。
