## 〇、总览：对象的一生

理不清的根本原因，通常是**把构造函数当成了"普通函数"**。

它不是。它是对象生命周期的**钩子（hook）**——不是你调用它，是**编译器在特定时刻替你调用**。

```
分配内存 ─→ [构造函数] ─→ ... 使用 ... ─→ [析构函数] ─→ 释放内存
   ↑                                            ↑
进入作用域                                   离开作用域
（栈上 / 堆上）                               （栈上 / 堆上）
```

对应到 `Stacka`：

```cpp
{
    Stacka s;          // ① 默认构造：a=nullptr, top=0, capacity=0
    s.StackInit(10);   // ② 手动申请堆内存（这一步在 C++ 里应该交给构造函数）
    s.push(1);
}                      // ③ 离开作用域，~Stacka() 被编译器自动插入，delete[] a
```

**关键认知**：你从来没有手写过 `s.~Stacka();`，是编译器在 `}` 处插进去的。

> 这就是 **RAII**（Resource Acquisition Is Initialization，资源获取即初始化）的雏形：
> 把"资源的申请"绑定到构造函数，"资源的释放"绑定到析构函数。
> 只要对象正常死亡，资源就一定会被释放——**哪怕中途 return、抛异常**。

## 一、类的定义与访问限定符

```cpp
// class 默认访问权限是 private
// struct 默认访问权限是 public（C++ 为了兼容 C 保留了 struct，但它也是类）
class Stacka
{
    public:              // 公有：类外可以访问
        void push(const int &val);
    private:             // 私有：只有类内成员函数能访问
        int *a;
        int top;
        int capacity;
};                       // ← 这个分号不能忘！
```

### 封装：为什么要分 public / private

```cpp
// 反面教材：成员全 public
// Stacka s;
// s.top = 999;        // 外部随意篡改内部状态 → 对象直接失控
```

封装的意义是**把"能做什么"和"怎么做的"分开**：

| | 对外暴露（public） | 对外隐藏（private） |
|---|---|---|
| 内容 | `push` / `pop` / `StackTop` | `a` / `top` / `capacity` |
| 意义 | **接口**（契约） | **实现**（随时可改） |
| 类比 | 遥控器上的按钮 | 电视内部的电路板 |

> **工程视角**：只要 `private` 部分的实现改了，外部代码一行都不用动。
> 这就是"可维护性"的第一块基石。

### 访问限定符的作用域

`public:` / `private:` 修饰的是**从它开始到下一个限定符之前**的所有成员，而不是某一行。

```cpp
class A
{
    public:
        int x;      // public
        int y;      // public
    private:
        int z;      // private
        int w;      // private
        // 后面没写限定符了 → 还是 private
};
```

## 二、this 指针

### 2.1 它从哪来

```cpp
class Date
{
    public:
        // 你写的：
        void DateInit(int year, int month, int day)
        {
            this->_year = year;   // this 是隐式的第一个参数
        }
        // 编译器眼中真实的形态：
        // void DateInit(Date* const this, int year, int month, int day)
    private:
        int _year, _month, _day;
};
```

`this` 的类型是 `Date* const this`——**指针本身不能改，但指向的内容可以改**。

（`const` 在 `*` 后面修饰的是指针本身，就像 `int * const p`）

### 2.2 为什么需要它

成员变量在内存里**不属于对象本身**吗？不，属于。每个对象都有一份独立的 `_year/_month/_day`。

那 `d1.DateInit(...)` 和 `d2.DateInit(...)` 调用的是**同一份代码**，函数怎么知道该改哪个对象的 `_year`？

答案就是 `this`——调用时被隐式传入：

```cpp
d1.DateInit(2026, 9, 2);   // 编译器悄悄转成 DateInit(&d1, 2026, 9, 2)
d2.DateInit(2026, 9, 3);   // 编译器悄悄转成 DateInit(&d2, 2026, 9, 3)
```

```
        ┌──────────────┐
   d1   │  2026  9  2  │ ← this 指向这里
        └──────────────┘
        ┌──────────────┐
   d2   │  2026  9  3  │ ← this 指向这里
        └──────────────┘
              ↑
        [ 同一份 DateInit 代码 ]
```

### 2.3 三个要点

1. **`this` 只能在成员函数内部使用**，静态成员函数（`static`）没有 `this`。
2. **栈上不能显式定义 `this`**（它是编译器传的，不是变量）。
3. **`*this` 就是对象本身**，`return *this;` 就是返回当前对象——这是链式调用的基础（后面 `operator=` 会用到）。

## 三、六个默认成员函数（全景图）

**默认成员函数**：你**不写，编译器也会自动生成**的成员函数。

C++98 时代是 6 个：

| # | 函数 | 签名（以 `Stacka` 为例） | 作用 |
|---|---|---|---|
| 1 | 构造函数 | `Stacka()` | 初始化对象 |
| 2 | 析构函数 | `~Stacka()` | 清理资源 |
| 3 | **拷贝构造** | `Stacka(const Stacka&)` | 用已有对象**生**出新对象 |
| 4 | **拷贝赋值重载** | `Stacka& operator=(const Stacka&)` | 两个**已存在**对象间赋值 |
| 5 | 取地址重载 | `Stacka* operator&()` | 取普通对象地址 |
| 6 | const 取地址重载 | `const Stacka* operator&() const` | 取 const 对象地址 |

> 第 5、6 个几乎没人会重载，除非你想搞点"邪门"的东西，知道有这回事就行。

**C++11 又加了 2 个**（第 [十二节](#十二拓展移动语义与-raii) 展开）：

| # | 函数 | 签名 |
|---|---|---|
| 7 | 移动构造 | `Stacka(Stacka&&)` |
| 8 | 移动赋值重载 | `Stacka& operator=(Stacka&&)` |

### 重中之重：3 和 4

第 1、5、6 个编译器生成的版本**基本不会出问题**。
**出问题的永远是第 3、4 个**——因为默认版本做的是"浅拷贝"，而浅拷贝遇到指针时就是灾难（第八节详述）。

## 四、构造函数

### 4.1 职责与特征

- **函数名与类名相同**，没有返回值（连 `void` 都不能写）
- **对象实例化时自动调用**，且**一生只调用一次**
- 可以重载（多个构造函数并存）

### 4.2 三种常见形式（对应 `Date` 类）

```cpp
class Date
{
    public:
        // 形式一：无参构造函数
        // 如果你写了带参的，编译器就不再生成这个了
        Date()
        {
            _year = 1; _month = 1; _day = 1;
        }

        // 形式二：带参构造函数
        Date(int year, int month, int day)
        {
            _year = year; _month = month; _day = day;
        }

        // 形式三：全缺省构造函数（你最终选的方案）
        // 它同时具备"无参构造"的能力，所以一个顶两个
        Date(int year = 1, int month = 1, int day = 1)
        {
            _year = year; _month = month; _day = day;
        }

    private:
        int _year, _month, _day;
};
```

> ⚠️ **坑**：形式一和形式三**不能同时存在**！
> 因为 `Date d;` 既匹配无参构造，也匹配全缺省构造 → **二义性，编译报错**。
> 你在代码里明智地注释掉了前两种，只留了全缺省——这是对的。

### 4.3 默认构造函数

**不用传参就能调用的构造函数**，都叫"默认构造函数"，有三种来源：

```cpp
Date() {}                          // ① 自己写的无参构造
Date(int y = 1, int m = 1, int d = 1) {}  // ② 自己写的全缺省构造
// ③ 自己一个都不写，编译器自动生成（对内置类型不做处理！）
```

**注意 ③ 的坑**：编译器生成的默认构造对 `int`/`double` 等内置类型**不做初始化**，值是随机的：

```cpp
class A { public: int x; private: int y; };
A a;          // 编译器生成的默认构造：a.x 和 a.y 都是随机值！

// C++11 补丁：成员声明处给缺省值
class B
{
    public:
        int x = 0;    // ← 声明处给缺省值
    private:
        int y = 0;
};
B b;          // b.x = 0, b.y = 0
```

> 对比你的 `Stacka`：虽然你写了 `Stacka()` 并把 `a` 初始化为 `nullptr`，
> 但如果你**没写**这个构造函数，`a` 就是**野指针**，析构时 `delete[] a` 直接崩。
> **指针成员一定要初始化**——这是铁律。

### 4.4 ★ 初始化列表

这才是 C++ 构造函数**真正推荐的写法**：

```cpp
class Stacka
{
    public:
        Stacka()
            : a(nullptr), top(0), capacity(0)   // ← 初始化列表
        {
            // 函数体——这里是"赋值"，不是"初始化"
        }

        // 对比你 Date 里写的（赋值风格）：
        Date(int year = 1, int month = 1, int day = 1)
        {
            _year = year;    // ← 这是赋值！虽然对 int 结果一样
        }
    private:
        int *a;
        int top;
        int capacity;
};
```

#### 为什么必须用初始化列表？

**有些成员只能在初始化列表里初始化，在函数体里赋值会编译报错：**

```cpp
class Const
{
    public:
        // ❌ 错误：const 成员和引用成员必须初始化
        // Const(int n) { _x = n; _ref = n; }

        // ✅ 正确
        Const(int n) : _x(n), _ref(n) {}

    private:
        const int _x;      // ① const 成员
        int& _ref;         // ② 引用成员
        // ③ 没有默认构造函数的自定义类型成员，也必须走初始化列表
};
```

**即使不报错，两者也有本质区别：**

| | 初始化列表 | 函数体内赋值 |
|---|---|---|
| 动作 | **一次**：直接构造 | **两次**：先默认构造，再赋值 |
| 效率 | 高 | 低（对自定义类型） |
| 能力 | 能初始化一切成员 | 只能赋值 |

#### ★ 顺序陷阱

**成员的初始化顺序 = 在类里声明的顺序，而不是你在初始化列表里写的顺序！**

```cpp
class Bad
{
    public:
        // 初始化列表写的是 b(a)、a(10)
        // 但实际执行顺序是 a(10) → b(a)，因为声明顺序是 a 在前
        Bad() : b(a), a(10) {}      // ⚠️ 这里 b 拿到的 a 是未初始化的！UB

    private:
        int a;      // ← 先声明
        int b;      // ← 后声明
};
```

> 编译器会给出 `-Wreorder` 警告，**一定要把初始化列表的顺序写成和声明顺序一致**。
> 你的 `Stacka` 初始化列表是 `a, top, capacity`，声明也是 `a, top, capacity` ✅ 做得对。

### 4.5 ★ explicit：阻止隐式转换

```cpp
// 你的 Date 是单参数（全缺省）构造函数
class Date
{
    public:
        Date(int year = 1, int month = 1, int day = 1) { /* ... */ }
};

Date d = 5;      // 😱 居然能编译通过！5 被隐式转换成了 Date(5, 1, 1)
// 等价于 Date d = Date(5);
// 等价于 Date d(5);

// 你的 stack_ 同理：
// stack_ s = 10;    // 也能通过！10 被当成容量 n
```

**修正：加 `explicit`（显式）**

```cpp
explicit Date(int year = 1, int month = 1, int day = 1) { /* ... */ }

// Date d = 5;       // ❌ 现在编译报错，符合预期
// Date d(5);        // ✅ 显式调用依然可以
// Date d = Date(5); // ✅ 显式构造再拷贝
```

**工程规范**：

> **除非你有意允许隐式转换，否则单参数构造函数一律加 `explicit`。**
> 这是 Google C++ Style Guide 的明确要求，也是 Code Review 的高频意见。

`std::vector` 就是正面例子：`vector<int> v(10);` 创建 10 个元素，而不是"把 10 转换成 vector"。

## 五、析构函数

### 5.1 职责与特征

```cpp
class Stacka
{
    public:
        ~Stacka()          // 函数名 = ~类名
        {
            delete [] a;   // 释放构造函数（或 StackInit）申请的堆内存
        }
    private:
        int *a;
        int top;
        int capacity;
};
```

- **函数名是 `~类名`**，没有参数，没有返回值
- **一个类只能有 1 个析构函数**（不能重载）
- **对象生命周期结束时自动调用**，一生只调用一次
- **后进先出**：后创建的对象先析构

```cpp
// 析构顺序验证
Date d1(2026, 9, 2);
Date d2(2026, 9, 3);
Date d3(2026, 9, 4);
// 离开作用域 → d3 先析构，然后 d2，最后 d1（栈结构，后进先出）
```

### 5.2 什么时候需要写析构？

**判断标准：类里有没有向系统"借"来的资源？**

| 资源 | 需要析构吗 |
|---|---|
| `new` / `new[]` 出来的堆内存 | ✅ 必须 `delete` / `delete[]` |
| `malloc` 出来的内存 | ✅ 必须 `free` |
| 打开的文件（`fopen`） | ✅ 必须 `fclose` |
| 加锁的互斥量 | ✅ 必须解锁 |
| 只是 `int` / `double` 等内置类型 | ❌ 不需要 |
| `std::string` / `std::vector` 成员 | ❌ 不需要（它们自己会管） |

对应你的代码：

- `Stacka` 里有 `int *a`（`new[]` 来的）→ **必须写析构** ✅ 你写了
- `stack_` 里有 `int* _a`（`malloc` 来的）→ **必须写析构** ✅ 你写了
- `Date` 只有三个 `int` → **不需要析构** ✅ 你的注释写对了

### 5.3 ★ `delete[] nullptr` 安全吗？

```cpp
~Stacka()
{
    delete [] a;   // 如果 a 是 nullptr 呢？
}
```

**安全。** C++ 标准明确规定：**`delete` / `delete[]` 一个空指针是合法的空操作。**

```cpp
int* p = nullptr;
delete p;      // ✅ 合法，什么也不做
delete[] p;    // ✅ 合法，什么也不做
```

所以你的 `Stacka s;`（此时 `a == nullptr`）直接析构**不会崩**。
这也是为什么构造函数里要把指针初始化成 `nullptr`——不是可选项，是**保命措施**。

> 但注意：`delete` 一个**野指针**（未初始化的随机值）或**重复 delete** 就是 UB（未定义行为），大概率崩溃。

### 5.4 ★ `new[] / delete[]` 与 `malloc / free` 不能混用

你的两个类用了两套体系：

```cpp
// Stacka：new[] / delete[] 配对 ✅
a = new int[cap];
delete [] a;

// stack_：malloc / free 配对 ✅（但 C++ 里不推荐）
_a = (int *)malloc(sizeof(int) * n);
free(_a);
```

**每一套各自配对是对的，但绝对不能交叉：**

```cpp
int* p = new int[10];
free(p);        // 💀 UB，可能直接崩

int* q = (int*)malloc(sizeof(int) * 10);
delete[] q;     // 💀 UB
```

**为什么不能混？**（面试常考）

- `new[]` 会在返回的指针**前面**多分配一小块空间，记录"数组有多少个元素"（析构时要知道调几次析构函数）
- `delete[]` 会往回偏移去读这个数字；而 `free` 不会 → 内存管理器直接崩溃
- `new` 还会调用构造函数，`malloc` 不会

> **C++ 中应当优先用 `new[] / delete[]`**，`malloc / free` 是 C 的遗留。
> 对 `int` 这种 POD 类型两者效果一样，但对有构造函数的类型，`malloc` 就是灾难：
> ```cpp
> std::string* p = (std::string*)malloc(sizeof(std::string) * 3);
> // 💀 构造函数根本没被调用，p[0] 是垃圾内存
> ```

## 六、拷贝构造函数

### 6.1 定义

```cpp
// 你的 Stacka 拷贝构造
Stacka(const Stacka& other)
    : a(other.capacity > 0 ? new int[other.capacity] : nullptr),
      top(other.top),
      capacity(other.capacity)
{
    for(int i = 0; i < top; i++)
    {
        a[i] = other.a[i];
    }
}
```

**特征：**

- 函数名 = 类名
- **参数必须是"同类型对象的引用"**，通常是 `const 类名&`
- 只有一个参数（否则就不是拷贝构造了）

### 6.2 ★ 为什么参数必须是引用？—— 会无限递归

```cpp
// 假设写成按值传参（错误示范）
Stacka(Stacka other)    // 💀
{
    // ...
}

// 调用 Stacka s2(s1) 时：
//   传参需要把 s1 拷贝一份给 other
//   → 拷贝一个 Stacka 又要调用拷贝构造
//   → 又要拷贝一份给 other...
//   → 无限递归，栈溢出
```

**加 `const` 的理由**：既能接受 const 对象，又能接受临时对象（右值）。
不加 `const` 的话，`Stacka s2 = s1 + s2;`（临时对象）就拷贝不了。

### 6.3 ★★ 最容易混的点：什么时候调用拷贝构造？

```cpp
Stacka s1;              // 默认构造函数
Stacka s2(s1);          // ① 拷贝构造 —— 括号形式

Stacka s3 = s1;         // ② 拷贝构造！⚠️ 虽然写着 =，但这是初始化不是赋值！
s3 = s1;                // ③ 拷贝赋值 —— 两个对象都已存在

void func(Stacka s);    // ④ 按值传参 → 拷贝构造
Stacka func2() { ... }  // ⑤ 按值返回 → 拷贝构造（可能被编译器优化掉）
```

#### 判断口诀

> **看左边：变量第一次出现（诞生）→ 拷贝构造；变量已经存在（活了）→ 拷贝赋值。**

```
Stacka s3 = s1;
       ↑
    第一次出现 → 诞生 → 拷贝构造

s3 = s1;
↑
   已经存在 → 存活 → 拷贝赋值
```

**为什么 `Stacka s3 = s1;` 不能是 `operator=`？**
因为 `operator=` 的前提是**两个对象都已经构造完毕**。而 `s3` 此刻还没有被构造，它是"正在出生"的对象。
C++ 规定：**用同类型对象初始化另一个对象，走拷贝构造。**

#### 用打印验证（强烈建议动手做）

```cpp
#include <iostream>
using namespace std;

class Demo
{
    public:
        Demo()                          { cout << "默认构造" << endl; }
        Demo(const Demo&)               { cout << "拷贝构造" << endl; }
        Demo& operator=(const Demo&)    { cout << "拷贝赋值" << endl; return *this; }
        ~Demo()                         { cout << "析构" << endl; }
};

Demo func(Demo d)   // ④ 按值传参：形参是一次拷贝构造
{
    return d;       // ⑤ 按值返回：可能又一次拷贝构造（RVO/NRVO 可能省略）
}

int main()
{
    Demo d1;            // 默认构造
    Demo d2(d1);        // 拷贝构造
    Demo d3 = d1;       // 拷贝构造 ← 重点观察！
    d3 = d1;            // 拷贝赋值
    func(d1);           // 拷贝构造（传参）+ 析构
    return 0;
}
```

> **亲眼看到输出，比看十遍书都管用。**

### 6.4 编译器生成的拷贝构造是什么样？

**逐成员拷贝（member-wise copy）**——把每个成员分别拷贝一份：

```cpp
// 编译器自动生成的版本（伪代码）
Stacka(const Stacka& other)
{
    a = other.a;              // ← 只拷贝了指针的值！
    top = other.top;
    capacity = other.capacity;
}
```

**这就是"浅拷贝"。** 对 `Date` 这种只有 `int` 的类完全够用，但 `Stacka` 里有个指针 → **灾难**（下一节详解）。

## 七、赋值运算符重载

### 7.1 为什么是"重载"

`=` 原本只能用于内置类型：

```cpp
int a = 10;    // 内置类型，编译器知道怎么办
```

自定义类型怎么赋值？**把 `=` 当成一个函数名，重载它**。

```cpp
Date d1(2026, 9, 1);
Date d2(2026, 9, 2);
d1 = d2;
// 编译器眼中的形态：
d1.operator=(d2);   // ← 真正的调用形式
```

### 7.2 你自己写的 `Date::operator==` 就是同一个机制

```cpp
// 你的代码
bool operator==(const Date& d2) const
{
    return _year == d2._year
        && _month == d2._month
        && _day == d2._day;
}

// 调用：d2 == d3
// 实际：d2.operator==(d3)   ← 简写形式
```

运算符重载的**本质**就是——**给运算符起一个叫 `operator@` 的函数名**。

```cpp
d2 == d3    ⟺  d2.operator==(d3)      // 写成成员函数（你现在的做法）
d2 == d3    ⟺  operator==(d2, d3)     // 写成全局函数（你注释掉的方案一/二）
```

你的注释里记录了三种方案：

| 方案 | 做法 | 问题 |
|---|---|---|
| 一 | 成员改 public | ❌ 破坏封装 |
| 二 | 加 `Getyear()` 等接口 | ⚠️ 能跑，但啰嗦，且 `==` 被写在类外 |
| 三 | 写成成员函数 | ✅ 你的最终选择，最优 |

> **工程提示**：`operator==` 写成成员函数是标准做法；
> 但 `operator<<` 输出运算符**必须**写成全局函数（因为左操作数是 `ostream`，不是你的类）。
> ```cpp
> ostream& operator<<(ostream& out, const Date& d)  // 全局函数
> {
>     out << d.Getyear() << "-" << d.Getmonth() << "-" << d.Getday();
>     return out;   // 返回 out 支持连续输出：cout << d1 << d2
> }
> ```

### 7.3 `Stacka::operator=` 逐行精读

```cpp
Stacka& operator=(const Stacka& other)
{
    if(this != &other)                          // ① 自赋值检查
    {
        Stacka temp(other);                     // ② 拷贝一份完整副本
        std::swap(a, temp.a);                   // ③ 交换指针
        std::swap(top, temp.top);
        std::swap(capacity, temp.capacity);
    }                                           // ④ temp 析构，释放旧内存
    return *this;                               // ⑤ 返回自身，支持链式赋值
}
```

#### ① 为什么返回 `Stacka&`？

支持**链式赋值**：

```cpp
a = b = c;
// 实际：a.operator=( b.operator=(c) );
// 若返回 void，a = (b = c) 就没法编译
```

返回类型也**不能用 `Stacka`（按值返回）**——那会再调用一次拷贝构造，且改的不是原对象。

#### ② 为什么是"先拷贝、再交换"（copy-and-swap 惯用法）？

**对比错误写法：**

```cpp
// ❌ 错误示范：先删后建
Stacka& operator=(const Stacka& other)
{
    delete [] a;                        // ① 先把旧内存释放了
    a = new int[other.capacity];        // ② 万一这里抛异常（内存耗尽）→ 对象已废
    top = other.top;
    capacity = other.capacity;
    for(int i = 0; i < top; i++)
        a[i] = other.a[i];
    return *this;
}
```

**这个写法有两个致命问题：**

| 问题 | 说明 |
|---|---|
| **自赋值灾难** | `s = s;` 时，第 ① 步 `delete[] a` 把自己内存释放了，第 ② 步再去读 `other.a`（就是自己）→ **读已释放内存，UB** |
| **异常不安全** | 第 ② 步 `new` 失败抛异常，`*this` 已经处于"半死不活"状态 |

**copy-and-swap 的妙处：**

```
执行前：  this->a ──→ [旧内存]        temp.a ──→ [新拷贝]
                                ↓ swap
执行后：  this->a ──→ [新拷贝]        temp.a ──→ [旧内存]
                                            ↓ temp 析构
                                        [旧内存被释放] ✅
```

- **异常安全**：`new` 在 `temp` 构造里完成，失败了 `*this` 丝毫未动 → **强异常保证**
- **自赋值安全**：即使不加 `if` 检查也正确（只是多做一次无用拷贝）

#### ③ `if(this != &other)` 是必需的吗？

**不是必需，是优化。**

copy-and-swap 本身已经能正确处理自赋值（`temp` 拷贝一份自己，swap 后 `temp` 持有原内存，析构释放 → 结果正确，只是白干一次）。
加上这行判断，**自赋值时直接跳过，省掉一次无用拷贝**。

> **面试点**：能说清"它为什么不是必需的，以及不加会有什么代价"，比单纯说"防止自赋值"高一个层次。

#### ④ 更简洁的惯用写法

```cpp
// 按值传参版：参数本身就是副本
Stacka& operator=(Stacka other)   // ← 注意：没有 &，参数是值传递
{
    std::swap(a, other.a);
    std::swap(top, other.top);
    std::swap(capacity, other.capacity);
    return *this;
}
// 少了一个临时变量、一个 if 判断，语义完全一样
```

**代价**：参数是按值传递的，即使是右值（临时对象）也会被拷贝。不过 C++11 有了移动语义后，这个代价也被消除了（见第十二节）。

### 7.4 ★ 拷贝构造 vs 拷贝赋值（对比表）

| | 拷贝构造 | 拷贝赋值 |
|---|---|---|
| **调用时机** | 对象**诞生**时 | 对象**已存在**时 |
| **典型写法** | `Stacka s2(s1);`<br>`Stacka s2 = s1;` | `s2 = s1;` |
| **当前对象状态** | 全新的，成员未初始化 | 已有资源，**必须先释放旧的** |
| **是否要自赋值检查** | 不需要（不可能是自己） | copy-and-swap 下不需要，但建议加 |
| **额外动作** | 无 | **释放旧资源** |

> **一句话记忆**：拷贝构造是"从零开始造一个"，拷贝赋值是"先把旧的拆了，再照着新的造"。

## 八、浅拷贝 vs 深拷贝（核心）

### 8.1 浅拷贝的灾难

假设 `Stacka` **没有**自己写拷贝构造：

```cpp
Stacka s1;
s1.StackInit(3);
s1.push(1); s1.push(2); s1.push(3);

Stacka s2(s1);   // 编译器生成的默认拷贝构造 → 浅拷贝
```

**内存状态：**

```
   栈区                    堆区
┌─────────────┐
│ s1: a ──────┼────────┐
│     top=3   │        │
│     cap=3   │        ↓
├─────────────┤    ┌───────────┐
│ s2: a ──────┼───→│  1  2  3  │  ← 两个对象共享同一块内存！
│     top=3   │    └───────────┘
│     cap=3   │        ↑
└─────────────┘        │
                    （同一块地址）
```

**接下来会发生什么？**

```cpp
}  // s2 先析构 → delete[] a  ✅ 成功释放
   // s1 再析构 → delete[] a  💀 double free → 程序崩溃（或内存管理器报错）
```

更隐蔽的是：如果你通过 `s1.push(4)` 修改数据，`s2` 也会"莫名其妙"地跟着变——因为它们根本就是同一块内存。

### 8.2 深拷贝：你的解决方案

```cpp
Stacka(const Stacka& other)
    : a(other.capacity > 0 ? new int[other.capacity] : nullptr),  // ① 自己申请新内存
      top(other.top),
      capacity(other.capacity)
{
    for(int i = 0; i < top; i++)
    {
        a[i] = other.a[i];                                        // ② 把内容复制过来
    }
}
```

**内存状态：**

```
   栈区                    堆区
┌─────────────┐
│ s1: a ──────┼───────→ ┌───────────┐
│     top=3   │         │  1  2  3  │  ← s1 专属
│     cap=3   │         └───────────┘
├─────────────┤
│ s2: a ──────┼───────→ ┌───────────┐
│     top=3   │         │  1  2  3  │  ← s2 专属
│     cap=3   │         └───────────┘
└─────────────┘
```

**现在两个对象完全独立：** 各自析构各自的，改一个不影响另一个。

### 8.3 一句话总结

> **浅拷贝 = 只拷指针（地址）**
> **深拷贝 = 不只拷指针，还拷指针指向的那块内容**

```
浅拷贝：  [a] ──┐
                ├──→ [同一块数据]   💀 会 double free
          [a] ──┘

深拷贝：  [a] ──────→ [数据副本1]   ✅ 互不干扰
          [a] ──────→ [数据副本2]
```

### 8.4 你的代码里，两种应对策略都有

| 类 | 有资源吗 | 你的做法 | 评价 |
|---|---|---|---|
| `Date` | 无（3 个 `int`） | 自己写了拷贝构造 | **多余**，编译器默认的逐成员拷贝就够 |
| `Stacka` | 有（`new[]` 的 `a`） | **深拷贝** + 拷贝赋值 | ✅ **正确**，符合三法则 |
| `stack_` | 有（`malloc` 的 `_a`） | **`= delete` 禁止拷贝** | ✅ **也是正确的**，另一种取舍 |

#### `stack_` 的做法：直接禁止拷贝（C++11）

```cpp
stack_(const stack_&) = delete;             // 删除拷贝构造
stack_& operator=(const stack_&) = delete;  // 删除拷贝赋值
```

`= delete` 是 C++11 的**删除函数**语法：明确告诉编译器"这两个函数不许生成"。

```cpp
stack_ s1(10);
stack_ s2(s1);    // ❌ 编译报错：调用被删除的函数
```

**这是非常正确的工程决策**——比起写出一个会崩溃的浅拷贝，**直接禁止**要安全得多。

**代价**：对象不能按值传递、不能返回、不能放进 `std::vector`。
**适用场景**：独占型资源（文件句柄、互斥锁、`std::thread`、`std::unique_ptr`）。

> **`std::unique_ptr` 就是这么干的**——禁止拷贝，只允许移动。

#### 两条路怎么选？

```
你的类里有指针/资源
        │
        ├── 需要"复制"语义（像值一样可拷贝）
        │       → 写深拷贝（三法则）        【Stacka 走的路】
        │
        └── 资源天然独占，不该被复制
                → = delete 禁止拷贝          【stack_ 走的路】
                → 或者用智能指针，实现 Rule of Zero
```

### 8.5 关于 `Date`：为什么自己写拷贝构造是多余的？

```cpp
// 你写的
Date(const Date& d)
{
    _year = d._year;
    _month = d._month;
    _day = d._day;
}

// 编译器自动生成的（逐成员拷贝）——完全一样
Date(const Date& d)
{
    _year = d._year;
    _month = d._month;
    _day = d._day;
}
```

**你把编译器本来就会做的事，手写了一遍。**

学习阶段写一遍**很有价值**——你得知道"默认版本长什么样"。但在生产代码里，这属于**冗余代码**。

> **修正建议**：`Date` 的拷贝构造可以直接删掉，行为完全不变。
> ```cpp
> // Date(const Date& d) { ... }   ← 删掉
> ```
> 用初始化列表的写法也更惯用：
> ```cpp
> Date(const Date& d) : _year(d._year), _month(d._month), _day(d._day) {}
> ```

## 九、三法则 / 五法则 / 零法则

### 9.1 三法则（Rule of Three）

> **如果你需要自己写析构函数，那么你几乎一定也需要自己写拷贝构造和拷贝赋值。**

**推理链：**

```
需要写析构函数
    ↓
说明类里管理着"需要手动释放的资源"（指针/句柄）
    ↓
那么默认的浅拷贝一定会出问题（double free）
    ↓
所以必须自己写拷贝构造 + 拷贝赋值，改为深拷贝
```

反过来也成立：

```
不需要写析构函数（如 Date）
    ↓
说明类里没有需要手动释放的资源
    ↓
默认的逐成员拷贝就是正确的
    ↓
所以不该自己写拷贝构造/拷贝赋值
```

**用你的代码验证：**

| 类 | 需要析构？ | 需要拷贝构造？ | 你的做法 | 符合三法则吗 |
|---|---|---|---|---|
| `Date` | ❌ | ❌ | 写了 | ❌ 多余 |
| `Stacka` | ✅ | ✅ | 写了深拷贝 | ✅ 正确 |
| `stack_` | ✅ | ✅（但选择禁止） | `= delete` | ✅ 合理 |

### 9.2 五法则（Rule of Five，C++11）

有了移动语义后，三法则扩展为五法则：

```
析构函数 + 拷贝构造 + 拷贝赋值 + 【移动构造】 + 【移动赋值】
                                    ↑ 新增
```

**判断**：如果你写了三法则中的任意一个，就应该考虑是否需要移动语义（见第十二节）。

### 9.3 零法则（Rule of Zero）★ 现代 C++ 的推荐做法

> **最好的做法是：一个都不写。**

**怎么做到？——用已经管好资源的成员，而不是裸指针。**

```cpp
// ❌ 旧写法：自己管理内存 → 必须写三法则（Stacka 现在的样子）
class StackOld
{
    public:
        StackOld() : a(nullptr), top(0), cap(0) {}
        ~StackOld() { delete[] a; }
        StackOld(const StackOld& other) { /* 深拷贝，一大堆代码 */ }
        StackOld& operator=(const StackOld& other) { /* copy-and-swap，一大堆代码 */ }
    private:
        int* a;
        int top;
        int cap;
};

// ✅ 新写法：用 std::vector，一个析构/拷贝构造都不用写！
class StackNew
{
    public:
        void push(int val) { v_.push_back(val); }
        void pop()         { if(!v_.empty()) v_.pop_back(); }
        int  top() const   { return v_.back(); }
        bool empty() const { return v_.empty(); }
    private:
        std::vector<int> v_;      // ← vector 自己管好了内存
};
// 析构、拷贝构造、拷贝赋值 —— 编译器默认生成的全都正确！
```

**为什么？** `std::vector` 内部已经实现了三法则。编译器为 `StackNew` 生成的浅拷贝，实际调用的是 `vector` 的**深拷贝**——因为 `vector` 的拷贝构造是深拷贝。

> **对比**：`Stacka` 大约 40 行管理内存的代码，`StackNew` 只需要一行 `std::vector<int> v_;`。

**Rule of Zero 的核心思想：**
> 让每个类只负责一件事。**资源管理交给专门的类**（`std::vector` / `std::string` / `std::unique_ptr` / `std::shared_ptr`），
> 你自己的业务类就不需要写任何析构/拷贝/移动函数了。

**但注意**：理解三法则仍然极其重要——因为**你迟早要写那个"管理资源的类"**（比如自己实现 `vector`、实现一个连接池）。而且面试必考。

## 十、const 成员函数

### 10.1 语法与本质

```cpp
// 你的 Date 类
int Getyear() const      // ← const 写在参数列表后面
{
    return _year;
}
```

**`const` 修饰的其实是 `this` 指针：**

```cpp
int Getyear() const
// 编译器眼中的形态：
int Getyear(const Date* const this)
//           ↑ 指向的内容也不能改了
```

对比非 const 成员函数：

```cpp
void setYear(int y)      { _year = y; }
// void setYear(Date* const this, int y)   ← 指向的内容可以改
```

**所以：const 成员函数内不能修改任何成员变量**（除非该成员被 `mutable` 修饰）。

### 10.2 为什么必须加 —— 你的代码里的实际问题

```cpp
int StackTop()      // ← 你写的，没有 const
{
    if(top == 0) { cout << "栈空" << endl; return -1; }
    return a[top-1];
}
```

它**没有修改任何成员**，所以逻辑上应该是 const 的。不加会怎样？

```cpp
void printStack(const Stacka& s)    // 接收 const 引用
{
    s.StackTop();     // ❌ 编译报错！
    // error: passing 'const Stacka' as 'this' argument discards qualifiers
}
```

**错误原因**：`const Stacka&` 承诺"我不修改你"，但 `StackTop()` 的 `this` 类型是 `Stacka* const`（可修改），
编译器不允许把"只读权限"的对象传给"可写权限"的函数——**权限不能放大**。

> 这和你在 `1.cpp` 笔记里写的引用权限规则是**同一条原理**：
> ```cpp
> const int a = 0;
> int &ar = a;         // ❌ 权限放大，编译报错
> const int& br = b;   // ✅ 权限缩小，可以
> ```

**修正：**

```cpp
int  StackTop() const;      // ✅ 不修改对象
void StackPrint() const;    // ✅ 只读
bool empty() const;         // ✅ 只读
int  size() const;          // ✅ 只读

void push(int val);         // 不加 const —— 它会修改对象
void pop();                 // 不加 const —— 它会修改 top
```

**判定方法**：**这个函数会修改对象的状态吗？不会 → 加 `const`。**

### 10.3 两条规则

| 规则 | 说明 |
|---|---|
| **const 对象只能调用 const 成员函数** | `const Stacka& s; s.push(1);` ❌ |
| **非 const 对象两个都能调** | 优先匹配非 const 版本 |

### 10.4 mutable：打破 const 的特例

```cpp
class Counter
{
    public:
        int getCount() const
        {
            ++count_;      // ✅ 合法：count_ 被 mutable 修饰
            return count_;
        }
    private:
        mutable int count_ = 0;   // 允许在 const 函数中修改
};
```

**用途**：缓存、统计计数、互斥锁（`mutable std::mutex mtx_;`——因为加锁不算"修改对象逻辑状态"）。

## 十一、我代码里的问题自查清单

> 按优先级排序，★ 越多越重要。

### `Stacka` 类

#### ⭐⭐⭐ 设计问题

**1. `StackTop()` 栈空返回 -1 —— 魔法值陷阱**

```cpp
int StackTop()
{
    if(top == 0) { cout << "栈空" << endl; return -1; }   // ⚠️
    return a[top-1];
}
```

**问题**：如果栈里真的存了 `-1`，调用者无法区分"栈顶是 -1"和"栈空"。

**三种生产级做法：**

```cpp
// 方案一：返回值 + 输出参数（C 风格，兼容性最好）
bool StackTop(int& out) const
{
    if(top == 0) return false;
    out = a[top-1];
    return true;
}
// 调用：if(s.StackTop(val)) { ... }

// 方案二：std::optional（C++17，语义最清晰）
std::optional<int> StackTop() const
{
    if(top == 0) return std::nullopt;
    return a[top-1];
}
// 调用：if(auto v = s.StackTop()) { use(*v); }

// 方案三：前置条件契约（STL 的做法，性能最高）
int StackTop() const
{
    // 调用者必须保证栈非空，否则 UB
    return a[top-1];
}
// std::vector::back() 就是这么设计的
```

**同理，`push` 栈满只 `cout` 一句就静默丢弃数据**——调用者完全不知道失败了。
应当返回 `bool`，或者**自动扩容**（像 `std::vector` 那样），或者抛异常。

**2. `StackInit` / `StackDestroy` 是 C 风格二段式初始化**

```cpp
Stacka s;
s.StackInit(10);    // 手动初始化
s.StackDestroy();   // 手动销毁
s.push(1);          // 💀 对 nullptr 解引用 —— 未定义行为！
```

**问题**：在 C++ 里，初始化的职责是**构造函数**的，清理的职责是**析构函数**的。
再提供一对 `Init/Destroy` 会造成**职责重叠 + 状态不一致**——编译器完全不知道对象已经"逻辑上死了"。

**修正**：删除这两个函数，用构造函数接收容量参数。

```cpp
explicit Stacka(int cap = 0)          // 构造函数直接接收容量
    : a(cap > 0 ? new int[cap] : nullptr),
      top(0),
      capacity(cap)
{}

void clear() { top = 0; }             // 需要"清空"就提供 clear()
```

**3. 没有扩容机制**

`push` 满了就丢弃数据。生产级实现应该像 `std::vector` 那样**成倍扩容**：

```cpp
void push(int val)
{
    if(top == capacity)
    {
        int newCap = capacity == 0 ? 4 : capacity * 2;   // 成倍扩容
        int* newA = new int[newCap];
        for(int i = 0; i < top; i++) newA[i] = a[i];
        delete[] a;
        a = newA;
        capacity = newCap;
    }
    a[top++] = val;
}
```

> **为什么成倍而不是每次 +1？** 均摊时间复杂度：成倍扩容是 O(1)，每次 +1 是 O(n)。

#### ⭐⭐ 接口规范问题

**4. 只读函数没加 `const`**

```cpp
int  StackTop() const;      // 加 const
void StackPrint() const;    // 加 const
void StackSize() const;     // 名字有问题，见下
```

**5. `StackSize()` 名不副实**

```cpp
void StackSize()                    // 名字像"查询大小"，实际在"打印"
{
    cout << "栈的大小为：" << top << endl;
}
```

**修正**：

```cpp
int size() const { return top; }        // 查询用这个
void PrintSize() const { ... }          // 打印就诚实叫 Print
```

**6. `push(const int& val)` —— 对 int 是负优化**

```cpp
void push(int val)      // ✅ int 是 4 字节，按值传递更惯用
```

`const&` 适合**大对象**（如 `std::string`、自定义结构体）。传引用本质是传地址，对 `int` 反而多一层解引用，还会阻止编译器优化。

> 一般规则：**内置类型按值传，类类型按 const 引用传。**

#### ⭐ 细节问题

**7. `NULL` → `nullptr`（C++11 起）**

```cpp

```

`NULL` 本质是宏 `0`，在函数重载决议时会退化成 `int`：
```cpp

```

**10. ⭐⭐ C++ 里应当用 `new[] / delete[]`，而不是 `malloc / free`**

## 十二、拓展：移动语义与 RAII

### 12.1 为什么需要移动语义

考虑这个操作：

```cpp
Stacka createStack() { Stacka s; s.StackInit(1000); return s; }

Stacka s = createStack();   // 拷贝构造 → 把 1000 个 int 又复制一遍，然后销毁临时的
```

**明明临时的那个对象马上就要死了，为什么不直接把它的指针"偷"过来呢？**

移动语义就是干这个的：**不复制资源，直接转移所有权**。

```cpp
// 移动构造（C++11）
Stacka(Stacka&& other) noexcept          // 参数是右值引用 &&
    : a(other.a), top(other.top), capacity(other.capacity)  // ① 直接偷指针
{
    other.a = nullptr;                   // ② 把源对象置空，防止它析构时释放
    other.top = other.capacity = 0;
}                                        // ③ 全程没有 new / 拷贝！
```

**对比：**

```
拷贝构造：           移动构造：
[src] ──→ [数据]     [src] ──→ nullptr      源对象被"掏空"
                          ↘
[新对象] ──→ [新副本]  [新对象] ──→ [原数据]  指针直接转移

代价：O(n) 拷贝       代价：几个指针赋值，O(1)
```

**`noexcept` 很关键**：移动构造必须声明不抛异常，否则 `std::vector` 扩容时不敢用它（因为一旦移动中途抛异常，原数据就损坏了）。

### 12.2 右值引用与 `std::move`

```cpp
Stacka a;
Stacka b(a);              // 左值 → 拷贝构造
Stacka c(std::move(a));   // std::move 把 a 转成右值 → 移动构造

// ⚠️ 注意：std::move 本身不移动任何东西！
// 它只是一个类型转换（static_cast<Stacka&&>），真正移动的是移动构造函数。
// 移动之后 a 处于"有效但未指定"的状态，不应该再使用（虽然可以安全地析构/赋值）
```

### 12.3 五法则

> **如果你写了三法则中的任意一个，考虑是否需要移动构造和移动赋值。**

完整版：

```cpp
class Stacka
{
    public:
        ~Stacka();                                    // ① 析构
        Stacka(const Stacka&);                        // ② 拷贝构造
        Stacka& operator=(const Stacka&);             // ③ 拷贝赋值
        Stacka(Stacka&&) noexcept;                    // ④ 移动构造 (C++11)
        Stacka& operator=(Stacka&&) noexcept;         // ⑤ 移动赋值 (C++11)
};
```

> **一个坑**：如果你只实现了拷贝构造，**编译器不会自动生成移动构造**（因为拷贝构造的存在说明这个类有特殊逻辑）。
> 所以 `std::move` 会退化成拷贝构造——你以为在移动，其实在拷贝。

### 12.4 RAII：C++ 最核心的资源管理思想

> **RAII = Resource Acquisition Is Initialization**
> **资源在构造函数中获取，在析构函数中释放。**

```cpp
// 你的 Stacka 已经是 RAII 了：
Stacka(const...)   // ← 构造函数负责申请
~Stacka()          // ← 析构函数负责释放
```

**RAII 的价值：** 即使中途发生异常或提前 return，析构函数也一定会被调用。

```cpp
void func()
{
    Stacka s;
    s.StackInit(100);
    riskyOperation();     // ← 这里抛异常了
    return;               // ← 或者提前 return 了
}                         // ✅ s 的析构函数依然会被调用，内存不会泄漏
```

**C++11 的智能指针就是 RAII 的标准化产物：**

```cpp
// 裸指针（需要手动管理）
int* p = new int(10);
// ... 中间 return / 抛异常 → 内存泄漏
delete p;

// unique_ptr（RAII，自动释放）
std::unique_ptr<int> p = std::make_unique<int>(10);
// ... 中间 return / 抛异常也没事
// 出作用域自动 delete ✅
```

| 智能指针 | 语义 | 对应你的哪个类 |
|---|---|---|
| `std::unique_ptr` | 独占所有权，**禁止拷贝** | `stack_`（`= delete` 的思路） |
| `std::shared_ptr` | 共享所有权，引用计数 | — |
| `std::vector` | 动态数组，**深拷贝** | `Stacka`（深拷贝的思路） |
